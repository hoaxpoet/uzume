# Increment BUG087.4 — the analysis clock, decoupled from tap arrival

**Type:** fix (defect) · engine / audio path

**Objective.** After this session, `.localFilePlayback` drives the MIR chain from the decoded file
at the smoothed playhead at render rate, instead of from AVAudioEngine tap arrival. A local-file
session's `FeatureVector` columns change at ≥ 50 Hz where they now change at ~10 Hz, and the 100 ms
staircase in every preset's audio coupling is gone. Streaming is untouched.

## 4. The premise, stated so it cannot be re-derived wrongly

**The defect is CADENCE, not staleness.** `FFTProcessor.process` fills its window from
`max(0, count - fftLength)` — the *newest* 1024 samples of each delivered buffer — so a buffer is
analysed at its own leading edge and audio is **not** old on arrival. What is wrong is that nothing
happens between arrivals: fields freeze ~100 ms, adding ~50 ms of lag on average and a visible
staircase.

**Any design premised on "the audio is stale when we see it" is aimed at the wrong thing.**

Measured basis (do not re-measure unless something contradicts it):

| | local file | streaming |
|---|---|---|
| feature change rate | **10.1 Hz** | 58.8 Hz |
| render | 59.8 fps | 59.9 fps |

Honest ceiling for this increment: **~40–50 ms of the ~145 ms** continuous-primitive lag, plus
removal of the staircase. The remaining τ 77–116 ms is band smoothing, which **Matt has explicitly
declined to change** (*"i don't like that the smoothing constants will change the feel of every
preset - too risky"*). Do not quietly reduce it to make the numbers look better.

## 5. Tasks

### Task 1 — Prove the position source before building on it
Instrument `AVAudioPlayerNode.playerTime` through `PlaybackClockSmoother` on a real local file:
log/record the smoothed read position against elapsed wall time across a full file **including a
loop boundary**.

**Done when:** a recorded run shows the smoothed position monotone, never behind the audible
position, and never more than `maxDeadReckonSeconds` ahead — the same properties
`PlaybackClockSmootherTests` gates, but observed on this new consumer. **Commit and stop if drift
is unbounded** — a drifting read position desynchronises analysis, which is *worse* than being
uniformly late, and that outcome changes the design rather than the tuning.

### Task 2 — Read-ahead buffer
Add a bounded read-ahead over the decoded `AVAudioFile` so a 1024-frame read at the playhead is a
memory lookup, not file IO on a latency-sensitive thread.

**Done when:** a unit test drives the reader across a file end and a loop wrap and gets contiguous,
correctly-positioned samples; no read occurs on the audio or render thread.

### Task 3 — The clock, behind a flag
Drive `AudioInputRouter.onAudioSamples` from the reader at render rate in `.localFilePlayback` mode
**only**, behind an env flag (program house rule: new runtime behaviour ships behind a flag with a
one-increment A/B path).

**Done when:** with the flag off, behaviour is byte-identical to today; with it on, a local-file
session's feature-change rate is ≥ 50 Hz.

### Task 4 — The rate gate
Add the automated gate.

**Done when:** it measures **how often a `FeatureVector` column actually CHANGES across render
rows**, from a real recorded session. ⚠ **Not slice count.** BUG087.3 shipped a regression test
asserting `hz >= 40` from slice count that **passed while the live rate was 16.4 Hz** — that is the
exact failure this gate exists to avoid.

### Task 5 — Check the tap's other consumers before changing its role
`SilenceDetector` is fed from the router callback; `SignalHealthMonitor` watches the chain.

**Done when:** each consumer is named with file:line and shown either still fed or deliberately
re-pointed. This is the BUG-070 shape and the step LFSTEM.2 had to do. **Do not remove the tap in
this increment** — leave it installed and report whether it can go.

### Task 6 — Hard stop and report
Before any golden regeneration or preset-visible tuning: **stop and report.** A ~6× change in update
rate will move goldens across many presets; that is a separate decision.

## 6. Do NOT

- **Do not touch `BandEnergyProcessor` smoothing constants** (`rate30: 0.65/0.75/0.75`,
  `attenuatedSmoother: 0.95`). Matt declined this explicitly; it is the D-004 trade and it is his.
- **Do not change the streaming path.** It already runs at 58.8 Hz through a different capture path
  (`AudioHardwareCreateProcessTap`) and is not what BUG-087 is about.
- **Do not re-attempt buffer slicing.** BUG087.2/.3 measured it: computation rose to ~47 Hz and a
  preset still saw ~16 Hz, because every slice of a buffer lands at the same instant. *"The binding
  constraint is how often audio ARRIVES, not how finely it is sliced."*
- **Do not re-attempt "tap a different node."** Measured and eliminated: the mixer delivers on the
  identical 0.1 s cadence (4800 frames @48 kHz vs the player's 4410 @44.1 kHz), `outputNode`
  delivers nothing, and the requested size is ignored at both 1024 and 4096.
- **Do not touch `AudioFeatures+Analyzed.swift`.** It is **at** its 400-line cap; float 56 is the
  last pad. A new field needs the struct split first, and this increment needs no new field.
- Do not retire the tap (see Task 5).

⚠ `AVAudioSinkNode` is recorded as **inconclusive**, not eliminated — a plain second `connect` from
`mainMixerNode` **aborts with signal 6 rather than throwing**, and the fan-out gave zero callbacks.
If you try it, treat an abort as a stop, not as a puzzle to permute.

## 10. DECISION-NEEDED — surface at the hard stop (Task 6), not before

**Question:** once the local-file path updates ~6× faster, do you want the presets re-checked before
or after their goldens are regenerated?

- **Option A — you watch first, goldens after.** You see the change live on a few presets, and we
  only lock in the new pictures once you have said they look right. Slower, but nothing is
  regression-locked to a look you have not approved.
- **Option B — regenerate first, then watch.** The suite goes green immediately and the branch is
  mergeable sooner, but the goldens then encode whatever the new rate produced, approved or not.

**Recommendation: A.** PR.19 found Nebula's old goldens were identical across all three fixtures —
they had locked in a preset drawing almost nothing. A golden is only a regression guard if the
picture it encodes is one you want kept.

**Default if no reply:** A — stop after the rate gate is green and report, without regenerating.
